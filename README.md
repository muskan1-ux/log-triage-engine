# Log Triage Engine

AI-powered distributed log triage and incident engine. Consumes application logs from Kafka
at high throughput, deduplicates and routes them, and uses an LLM (via LangChain4j) to
automatically triage errors into a structured severity/root-cause/action assessment -
with circuit breakers, retries, and a dead-letter queue guarding every failure mode.

**Stack:** Java 17 - Spring Boot 3.5 - Apache Kafka - Redis - LangChain4j - PostgreSQL -
Resilience4j - Docker.

## Architecture

```
Log sources -> Kafka (logs.raw.v1) -> Consumer group -> Redis dedup -> Level router
                                                                          |
                                          -------------------------------+------------------------
                                          |                                                       |
                                INFO / WARN / DEBUG                                      ERROR / FATAL
                                          |                                                       |
                              Batched write to Postgres                          Bounded async executor
                                                                                            |
                                                                     Resilience4j (circuit breaker, retry,
                                                                       bulkhead, time limiter)
                                                                                            |
                                                                      LangChain4j -> LLM structured triage
                                                                               /              \
                                                                     saved to Postgres     DLQ (logs.dlq.v1)
                                                                    with severity/summary   on unrecoverable
                                                                    /root cause/action           failure
```

**Key design decisions:**

- **Consumer stays fast.** The `@KafkaListener` only does a Redis dedup check and hands
  ERROR/FATAL events to a bounded thread pool; it never blocks on an LLM call. This is a
  deliberate throughput-over-strict-delivery trade-off - see the javadoc on
  `LogProcessingService` for the failure mode it accepts and how to switch to
  stronger guarantees.
- **Backpressure is explicit.** The executor uses `AbortPolicy`; a full queue throws
  `RejectedExecutionException`, which is translated into a `RetryableProcessingException`
  that the Kafka `DefaultErrorHandler` retries with exponential backoff before giving up.
- **Two DLQ paths.** `DeadLetterPublishingRecoverer` catches synchronous listener failures
  (bad payloads, validation errors); `DlqProducer` catches asynchronous triage failures
  (circuit open, retries exhausted, LLM timeout) - both land on the same `logs.dlq.v1` topic
  with the original event plus exception metadata for replay.
- **Resilience4j wraps a plain Spring bean, not the LangChain4j proxy.** `LogTriageService`
  is a dynamic proxy generated by LangChain4j's `AiServices`, so `@CircuitBreaker` /
  `@Retry` / `@Bulkhead` / `@TimeLimiter` are applied on `LogTriageOrchestrator`, the Spring
  bean that wraps it - that's the only place Spring AOP can intercept the call.

## Running locally

```bash
export OPENAI_API_KEY=sk-...      # or leave unset to run with fallback triage only
docker compose up -d
```

This starts Kafka, Redis, Postgres, and the app on `localhost:8080`. Kafka auto-creates
`logs.raw.v1` and `logs.dlq.v1` with 6 partitions.

Publish a test error log:

```bash
curl -X POST localhost:8080/api/logs \
  -H "Content-Type: application/json" \
  -d '{
        "eventId": "evt-001",
        "service": "checkout-service",
        "host": "pod-7f9c",
        "level": "ERROR",
        "message": "Connection timed out talking to payments-service",
        "stackTrace": "java.net.SocketTimeoutException: connect timed out\n\tat ..."
      }'
```

Check the triage result:

```sql
SELECT event_id, severity, root_cause_category, suggested_action, confidence
FROM log_events WHERE event_id = 'evt-001';
```

Circuit breaker / retry / bulkhead health: `curl localhost:8080/actuator/health`

## Tests

```bash
mvn test
```

`LogProcessingServiceTest` exercises the dedup, level-routing, and backpressure logic
with mocked collaborators and a synchronous executor. `spring-kafka-test` and
Testcontainers (Kafka + Postgres) are on the test classpath for adding broker-level
integration tests.

## Notes / next steps

- Batch inserts are enabled via Hibernate `jdbc.batch_size`; for very high volume, swap
  `LogPersistenceService` for a micro-batching writer (buffer + scheduled flush) instead
  of one `save()` per event.
- `AckMode.RECORD` + Redis dedup gives at-least-once delivery with idempotent reprocessing.
  Switch to manual ack after `saveWithTriage()` for stronger guarantees at a latency cost
  (see `LogProcessingService` javadoc).
- Add a Grafana dashboard on top of the exposed `prometheus` actuator endpoint for
  circuit breaker state, triage latency, and DLQ volume.
